# Connections checklist

The repository is deliberately usable before every external service is connected. The core OS works now; these connections expand what it can observe and automate.

## Cloudflare

1. Deploy the Worker from GitHub Actions or Wrangler.
2. Apply D1 migrations with `npm run db:remote`.
3. Keep the public Worker route enabled.
4. For private access, change `REQUIRE_AUTH` to `true` and add `OS_ACCESS_TOKEN` as a Worker secret.
5. Optional: set `AI_MODE` to `workers-ai` to allow selected Ask Your History prompts to use Workers AI.

## Opportunity Radar bridge

The OS acts as Radar's internal source of truth instead of making the owner re-enter projects and demonstrated capabilities by hand.

`RADAR_URL` is committed as the public Radar origin. The credential is deliberately separate from every other token:

1. Generate one long random value (32+ characters).
2. Save it in Opportunity Radar as `RADAR_OS_SYNC_TOKEN`.
3. Save the exact same value in this Worker as secret `RADAR_SYNC_TOKEN`.
4. Deploy both sides.
5. Trigger `POST /api/radar/sync` once, or let normal OS activity trigger background syncs.

What syncs automatically:

- OS projects → Radar reusable assets.
- Project goals → Radar goals.
- Capabilities supported by real code/milestone records → Radar capabilities with evidence references and conservative confidence.
- Optional OS settings `radar.resources` and `radar.goals` → Radar resources/goals.

What does **not** happen:

- OS records never become external market evidence, so they cannot inflate Radar confidence or independent-source counts.
- The bridge does not invent production maturity. Automatically inferred capabilities are capped at `working` until stronger evidence or owner review promotes them.
- Missing resources remain unknown rather than being guessed as zero.

Diagnostics:

- `GET /api/health` includes `radarSyncConfigured`.
- `GET /api/radar/snapshot` shows exactly what the OS would send, without sending it.
- `POST /api/radar/sync` performs an immediate sync and returns Radar's response.

## GitHub auto-capture

There are now two layers.

### 1. Account-wide automatic discovery and activity

`GITHUB_OWNER` tells the OS which GitHub account belongs to the owner.

The OS automatically:

- discovers repositories and creates project contexts;
- polls recent GitHub activity hourly;
- captures useful pushes, pull requests, issues, releases and branch/repository creation/deletion;
- deduplicates activity by GitHub event ID;
- runs each new activity event through the same eight-agent intelligence pipeline;
- refreshes the Chief of Staff brief when new activity arrives;
- syncs the updated internal picture to Opportunity Radar.

Public repositories need no extra GitHub credential. Add Worker secret `GITHUB_TOKEN` later if private repository activity should also be visible to the OS.

`GITHUB_ACTIVITY_SKIP_REPOS` is a comma-separated list of repositories that already have instant webhooks and therefore should not be polled again. The current deployment skips `Operating-System` because that repository already has a webhook.

### 2. Instant repository webhooks

Use webhooks where immediate capture matters:

- Webhook URL: `https://YOUR-OS-DOMAIN/webhooks/github`
- Content type: `application/json`
- Secret: create a strong value and save the same value as Worker secret `GITHUB_WEBHOOK_SECRET`.
- Events: Pushes, Pull requests, Issues.

Webhook events are signed, deduplicated and processed immediately. Account-wide polling is the fallback/coverage layer for the rest of the public repositories.

Useful diagnostics:

- `GET /api/health` includes `githubInventoryConfigured` and `githubActivityConfigured`.
- `POST /api/github/activity/refresh` triggers an immediate activity pull when authorized by the OS/Radar machine token.
- `POST /api/github/inventory` accepts the safe repository inventory generated by the deployment workflow.

## GitHub Actions deployment

Repository settings → Actions secrets/variables:

- Secret `CLOUDFLARE_API_TOKEN`
- Secret `CLOUDFLARE_ACCOUNT_ID`
- Secret `OS_WEBHOOK_SECRET`
- Secret `RADAR_SYNC_TOKEN`
- Optional secret `OS_ACCESS_TOKEN`
- Variable `CLOUDFLARE_DEPLOY_ENABLED=true`

The deploy workflow applies migrations, syncs Worker secrets, deploys the Worker, verifies the public route, imports GitHub inventory and checks the Radar bridge.

## Remaining optional connectors

Recommended order after GitHub:

1. Calendar — commitments and time context.
2. Gmail — decisions, requests and follow-ups (user-selected scope only).
3. Drive/docs — specifications and durable source documents.
4. Voice capture — fastest mobile input.
5. R2 uploads — screenshots, images, audio, video and transcripts.
6. Vector search — only after the corpus is large enough to need semantic retrieval.
